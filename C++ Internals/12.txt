.hpp files (C++ header files) generally contain declarations of classes, functions, variables, templates, constants, etc., that are intended to be used across different source files in a project. They allow multiple .cpp files to know about these entities without putting their full definitions in every source file.
For example:
// Math.hpp
int add(int a, int b);   // declaration
// Math.cpp
int add(int a, int b) {  // definition
    return a + b;
}
// main.cpp
#include "Math.hpp"
int main() {
    add(2, 3);
}
Easy distinction:
.hpp → what exists / declarations
.cpp → how it works / definitions
Though in real C++, .hpp files can also contain definitions, especially for templates, inline functions, and class member functions defined inside the class.
why defintion also not in hpp?
Actually, definitions can be in .hpp files. The reason we often separate them is mainly to avoid multiple-definition problems and to keep compilation organized.
Suppose:
// Math.hpp
int add(int a, int b) {
    return a + b;
}
And both main.cpp and test.cpp do:
#include "Math.hpp"
Remember: #include essentially copies the header's contents into each .cpp file during preprocessing.
So the compiler effectively sees:
main.cpp → definition of add()
test.cpp → definition of add()
Then, when linking, there can be multiple definitions of add() → linker error.
That's why we commonly do:
// Math.hpp
int add(int a, int b);   // declaration
// Math.cpp
int add(int a, int b) {  // definition
    return a + b;
}
Now every .cpp file can know that add() exists, but there is only one actual definition compiled.
But there are important exceptions
Definitions do belong in headers in several cases:
// Math.hpp
inline int add(int a, int b) {
    return a + b;
}
inline allows the same definition to appear in multiple translation units.

A better mental model is:
.hpp exposes an interface and may also contain definitions that are safe/necessary to include in multiple translation units. .cpp usually contains definitions that should exist in only one translation unit.

.hpp files can contain definitions too, but we usually put shared declarations there and keep non-inline definitions in .cpp files to avoid multiple-definition errors. as the headers are copied into the source files it is included in, so there can be multiple definition error if we put definition in the hpp file.

Compiling files separately is particularly useful in large projects because only modified files and the files that depend on them need to be recompiled, while the rest remain unchanged as a result of which compilation time is saved.

A static library is basically a collection of already-compiled .o (object) files packaged into a single file, usually ending in .a on Linux. Its required code is copied into your executable during linking.

command like: g++ main.o -lbase -lcef -o app
Static library
A static library is a collection of already-compiled object files (.o) packaged into one file.
On Linux: libcef.a. The naming convention is: lib<name>.a
-lbase means: Find and link the library named libbase.a.

g++ main.o -lbase -lcef -o app tells the linker:
1. Take main.o.
2. Find libbase.a and link the required code from it.
3. Find libcef.a and link the required code from it.
4. Combine everything into an executable called app.


Why do we need libraries?
Suppose:
// main.cpp
#include "math.hpp"
int main() {
    add(2, 3);
}
main.cpp only knows the declaration:
int add(int, int);
But the actual implementation might be inside:
libmath.a
During linking:
g++ main.o -lmath -o app
the linker finds the actual implementation of add() in libmath.a.

Important distinction:
.hpp       → declarations
.cpp       → definitions
.o         → compiled definitions
.a         → collection of .o files
executable → linked result

So:
.cpp → compiler → .o
.o + .a → linker → executable

And static means the required library code is copied into the final executable at link time. You generally don't need the .a file when running the resulting executable.

Dynamic/shared library: libmath.so: The library remains separate, and the executable refers to it.

So the simple mental model is:

.o = compiled code
.a = collection of .o files (static library)
.so = shared/dynamic library
linker = combines your object files with required library code to create the executable

And one important thing: -lbase does not mean “use a file literally called base.” The -l option tells the linker to look for the conventional library name, such as libbase.a or libbase.so.

A shared library is a library whose compiled code is not copied into your executable. Instead, the executable refers to the library, which is loaded/shared at runtime. The library stays separate and is loaded when the program runs.
